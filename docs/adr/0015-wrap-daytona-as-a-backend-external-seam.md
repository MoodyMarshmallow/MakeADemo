# Wrap Daytona as a Backend External Seam

MakeADemo will provision and operate Daytona workspaces through a backend External Seam used by Repo Preparation, Script Generation, Capture Path Validation, and repair attempts, rather than treating Daytona setup as manual ops bootstrap outside the product. We chose this because agentic preparation and script repair depend on workspace lifecycle, command execution and logs, and teardown, and those behaviors need a small testable interface with fakes for pipeline tests.

The seam should hide Daytona-specific SDK or API calls from pipeline orchestration. Repo Preparation should depend on product-level workspace operations such as create, execute, stream logs, and release. The current development policy creates both sandboxes with network access enabled; dependency execution and release do not mutate or report network resealing.

Agent Harness runs backed by Daytona should still produce the existing Preparation Manifest, Demo Script, validation evidence, and workspace diff artifact. Daytona is the execution substrate, not a replacement for pipeline output contracts.

During early development, backend-owned run artifacts may persist provider-neutral Agent Harness output needed to diagnose agent behavior: assistant text, provider-exposed reasoning (raw or summary), diagnostics, tool names and lifecycle states, stage and provider/model identifiers, output lengths, activity kinds, and timestamps. The composition logging seam does not sanitize or redact that captured output, so these artifacts must remain in controlled development storage. Tool arguments and results are intentionally omitted from both human-readable output and durable audit artifacts. Pipeline artifacts such as validation evidence, browser-level network evidence, the final diff, and the Preparation Manifest remain separate product contracts rather than substitutes for the diagnostic agent transcript. Production retention and redaction policy must be resolved before these artifacts are exposed beyond controlled development use.

The backend seam should enforce bounded timeouts for post-provisioning agent work, including dependency installation, demo build, manifest generation, script generation, and repair attempts. An authorized backend dependency-install handoff receives one fresh inactivity budget, capped by the shared Repo Preparation hard deadline, covering toolchain inspection, trusted artifact provisioning, workspace synchronization, and immutable installation together. Substeps do not reset that budget. If a timeout fires, MakeADemo should cancel active sandbox commands, prevent later dependency substeps from starting, and tear down the Daytona workspace as part of cleanup. Shared cancellation and absolute pipeline deadlines retain precedence. It does not attempt to close outbound network access while Daytona sandbox-firewall Runtime Network Lockdown is deferred.

Dependency installation also has a backend-owned bounded execution profile for the 2-CPU, 4-GiB submitted-code Sandbox. The provider applies common native-build and Turbo limits after filtering caller input. Stable manager controls live in catalog-owned install arguments: npm 8–11 receives `--maxsockets=4`, pnpm 8–11 receives `--child-concurrency=2` and `--network-concurrency=4`, and Yarn Classic receives `--network-concurrency 4`. Yarn 2 and 3 receive only `YARN_NETWORK_CONCURRENCY=4`; Yarn 4 additionally receives `YARN_TASK_POOL_CONCURRENCY=2`, because earlier Berry generations reject that key. Repository or agent values cannot increase a claimed bound. Trusted registry provisioning rejects exact releases whose official metadata carries a non-empty `deprecated` field; the revisioned pnpm 11 default is therefore a vetted non-deprecated release rather than pnpm 11.13.0. It also maps an exact registry 404 or mismatched exact-version metadata to `package_manager_release_unavailable` without falling back to a nearby version. Revisioned defaults must themselves exist in the provisioned artifact family; Yarn 2 therefore defaults to the available `@yarnpkg/cli-dist@2.4.2`, not the nonexistent 2.4.3 release. Exit code 137 is classified conservatively as `dependency-install-sigkill`, because the status alone cannot prove an OOM kill; OOM pressure, provider termination, and another external kill remain possible. Its stdout and stderr tails are bounded by UTF-8 bytes, propagated as an inconclusive infrastructure disposition, and returned without spending another agent turn on a condition the model cannot repair.
